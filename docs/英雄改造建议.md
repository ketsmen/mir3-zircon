## 1. 项目背景

### 1.1 目标

将 Legend of Mir 2 中的英雄（Hero）系统移植到 Legend of Mir 3 Zircon 项目中，实现以下功能：

- 英雄创建（选择职业、性别、命名）
- 英雄召唤/收回
- 英雄控制（行为模式切换）
- 英雄装备系统（独立库存和装备栏）
- 英雄技能系统（自动施放）
- 英雄 AI（寻敌、攻击、自我增益、治疗）
- 英雄杀怪（经验获取、升级）
- 英雄和玩家之间的物品传输

### 1.2 源项目信息

- **Mir2 项目路径**：`D:\GitHub\mir2`
- **英雄系统核心文件**：约 30 个文件，涉及约 3298 行专用代码
- **英雄相关代码**：跨越 30+ 个文件

### 1.3 目标项目信息

- **Mir3 项目路径**：`D:\GitHub\mir3-zircon`
- **当前状态**：无英雄系统，有伴侣系统（仅拾取，非战斗）和宠物系统（召唤怪物）

## 2. 架构差异对比

### 2.1 对象继承体系

**Mir2 继承体系**：
```
MapObject (基类)
└── HumanObject (人类对象基类，包含装备、技能、战斗逻辑)
    ├── PlayerObject (玩家)
    └── HeroObject (英雄)
        ├── WarriorHero (战士英雄)
        ├── WizardHero (法师英雄)
        ├── TaoistHero (道士英雄)
        ├── AssassinHero (刺客英雄)
        └── ArcherHero (弓箭手英雄)
```

**Mir3 继承体系**：
```
MapObject (基类，1860 行)
├── PlayerObject (玩家，16958 行，直接继承 MapObject)
├── MonsterObject (怪物，3151 行)
│   └── Companion (伴侣，886 行，仅拾取非战斗)
│   └── [100+ 怪物子类]
├── NPCObject
├── SpellObject
└── ItemObject
```

**关键差异**：Mir3 没有 `HumanObject` 中间类，`PlayerObject` 直接继承 `MapObject`。

### 2.2 功能对比表

| 功能 | Mir2 实现 | Mir3 现状 | 移植影响 |
|------|----------|-----------|---------|
| 英雄对象类 | HeroObject : HumanObject | 不存在 | 需要新建 |
| 英雄数据库 | HeroInfo : CharacterInfo | 不存在 | 需要新建 |
| 英雄 AI | ProcessAI → ProcessSearch → ProcessAttack | MonsterObject.ProcessAI | 可参考 |
| 英雄魔法 | 独立实现 | MagicObject 抽象类 | 需要适配 |
| 英雄装备 | HeroEquipment/HeroInventory 网格类型 | 不存在 | 需要新建 |
| 英雄行为模式 | HeroBehaviour 枚举（4 种） | PetMode 枚举（5 种） | 可复用 |
| 宠物系统 | SummonedMonster 类 | MonsterObject + PetOwner | 模式不同 |
| 伴侣系统 | 无 | Companion : MonsterObject（仅拾取） | 可参考框架 |
| 对象类型 | ObjectType.Hero = 8 | 5 种类型（无 Hero） | 需要新增 |

### 2.4 数据库对比

**Mir2 英雄数据库模型 (HeroInfo)**：

```
HeroInfo : CharacterInfo
├── AutoPot (bool) - 自动喝药开关
├── Grade (byte) - 英雄品质（0-3）
├── HPItemIndex (int) - 自动喝药 HP 物品索引
├── MPItemIndex (int) - 自动喝药 MP 物品索引
├── AutoHPPercent (byte) - HP 阈值百分比
├── AutoMPPercent (byte) - MP 阈值百分比
├── SealCount (ushort) - 封印次数
├── Inventory[] - 库存物品
├── Equipment[] - 装备物品
└── Magics[] - 已学习魔法
```

**Mir3 现有数据库模型**：
- `CharacterInfo`：无英雄相关字段
- `UserCompanion`：伴侣系统（非战斗）

## 3. 移植难度评估

### 3.1 难度等级说明

| 等级 | 说明 |
|------|------|
| 低 | 直接复制修改，逻辑简单 |
| 中 | 需要适配但逻辑相似，有一定工作量 |
| 高 | 需要重新设计或大量重写，风险较高 |

### 3.2 总体评估

**移植难度：中等偏高**

主要挑战：
1. Mir3 没有 HumanObject 基类，需要新建 HeroObject 或重构继承体系
2. 需要从零实现英雄 AI 系统
3. 需要重新实现所有英雄 UI（使用 Mir3 的自绘 DX 控件）

主要优势：
1. 可以复用现有的 MagicObject 魔法系统（190+ 技能）
2. 可以参考现有的 Companion 和宠物系统
3. 网络协议和数据库模式相对独立，易于扩展

## 6. 关键技术难点

### 6.1 HeroObject 继承体系设计

**难度：高**

**问题**：Mir2 的英雄继承自 HumanObject，但 Mir3 没有这个类。

**方案 A：创建 HumanObject 基类**

```
MapObject
└── HumanObject (新建)
    ├── PlayerObject (重构)
    └── HeroObject (新建)
```

- 优点：代码复用度高，与 Mir2 架构一致
- 缺点：需要重构 16000+ 行的 PlayerObject，风险大
- 工作量：5-10 天

**方案 B：HeroObject 直接继承 MapObject（推荐）**

```
MapObject
├── PlayerObject (不修改)
├── HeroObject (新建，借鉴 PlayerObject 和 MonsterObject)
└── MonsterObject
```

- 优点：不需要重构现有代码，风险小
- 缺点：可能有代码重复
- 工作量：3-5 天

**建议**：采用方案 B，参考 Mir3 现有的 Companion（886 行）和 MonsterObject（3151 行）的模式。

### 6.2 英雄 AI 系统

**难度：中**

**Mir2 英雄 AI 架构**：
```
HeroObject.Process()
├── ProcessAutoPot() - 自动喝药
├── ProcessStacking() - 堆叠处理
├── ProcessSearch() - 寻找目标
├── ProcessAI() - AI 主逻辑
│   ├── ProcessFriend() - 友方增益/治疗
│   └── ProcessAttack() - 攻击逻辑
├── ProcessTarget() - 执行攻击
└── ProcessRoam() - 跟随主人
```

**Mir3 可参考的实现**：
- `MonsterObject.ProcessAI()` - 怪物 AI 框架
- `Companion` 类 - 伴侣跟随逻辑
- `MonsterObject.PetOwner` - 宠物所有权模式

**实现建议**：
- 复用 MonsterObject 的 ProcessAI 框架
- 借鉴 Companion 的跟随逻辑
- 实现 ProcessSearch（寻敌）和 ProcessAttack（攻击）
- 为每个职业实现独立的 AI 子类

### 6.3 英雄魔法系统

**难度：中**

**问题**：Mir2 的英雄魔法是独立实现的，Mir3 使用 MagicObject 抽象类。

**解决方案**：
- 在 HeroObject 中维护 `Dictionary<MagicType, MagicObject> MagicList`
- 复用现有的 MagicObject 子类（FireBall、Heal、Slaying 等）
- AI 根据情况自动选择施放技能
- 英雄的魔法消耗和冷却独立于主人

**注意事项**：
- 英雄魔法的伤害计算可能需要调整
- 英雄魔法的消耗可能不同于玩家
- 需要处理英雄魔法的等级和经验

### 6.4 物品/装备系统

**难度：中**

**实现内容**：
- 新增 MirGridType.HeroEquipment 和 HeroInventory
- 修改客户端 DXItemCell 支持英雄网格类型
- 实现英雄和玩家之间的物品传输
- 处理物品绑定规则（某些物品不能给英雄）

**参考实现**：
- Mir2 的 TakeBackHeroItem 和 TransferHeroItem 数据包
- Mir3 现有的物品交易系统

### 6.5 UI 界面

**难度：中**

**Mir3 UI 系统特点**：
- 使用自研 DX 控件（DXControl、DXButton、DXLabel 等）
- 所有界面都是代码绘制，不使用 WinForms 设计器
- 支持 DirectX 渲染

**需要实现的 UI**：
- 英雄库存对话框（参考 InventoryDialog）
- 英雄装备对话框（参考 CharacterDialog）
- 英雄状态面板（参考 MainPanel 的 HP/MP 条）
- 英雄行为模式面板
- 英雄管理对话框
- 英雄创建对话框（参考角色创建）

**实现建议**：
- 继承现有的 DXWindow 或 DXControl
- 复用 DXItemGrid 和 DXItemCell 组件
- 参考现有对话框的布局和样式

3. **阶段 3：物品系统**（2-3 天）
   - 实现英雄库存和装备

### 8.2 技术决策建议

| 决策点 | 建议 | 理由 |
|-------|------|------|
| 继承体系 | HeroObject 直接继承 MapObject | 避免重构 PlayerObject，风险小 |
| 英雄类型 | ObjectType.Hero = 8 | 与 Mir2 一致，便于理解 |
| 英雄数量 | 默认 1 个，最多 9 个 | 与 Mir2 一致 |
| 英雄等级 | 独立于玩家等级 | 与 Mir2 一致 |
| 英雄经验 | 独立获取，可升级 | 与 Mir2 一致 |
| 英雄死亡 | 可复活，有复活延迟 | 与 Mir2 一致 |
| 英雄封印 | 暂不实现 | 降低初期复杂度 |
| 弓箭手职业 | 暂不实现（Mir3 无弓箭手） | 降低初期复杂度 |

## 9. 风险评估

### 9.1 风险清单

| 风险 | 等级 | 说明 | 缓解措施 |
|------|------|------|---------|
| PlayerObject 修改风险 | **高** | 16000+ 行的文件，修改需要谨慎 | 使用部分类或最小化修改 |
| 性能风险 | 中 | 多个英雄同时在线可能影响服务器性能 | 限制英雄数量，优化 AI 处理 |
| 兼容性风险 | 中 | 新增数据包和模型需要考虑版本兼容 | 使用新字段，不修改现有字段 |
| UI 工作量 | 中 | 自绘 UI 系统需要重新实现所有界面 | 参考现有对话框，复用控件 |
| 魔法系统适配 | 中 | 英雄魔法可能与玩家魔法有差异 | 仔细测试每个技能 |
| 数据库迁移 | 低 | 新增 HeroInfo 表不影响现有数据 | 使用新表，不修改现有表 |

- 英雄和玩家物品传输
- 英雄在不同地图的行为（NoHero 地图）
- 多英雄切换
- 英雄自动喝药
- 英雄与怪物/NPC/其他玩家的交互
